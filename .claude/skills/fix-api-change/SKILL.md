# fix-api-change

note 側の変更は正規化レイヤーに閉じ込め、公開型は変えないのが原則。

## 1. 差分を把握する

- Issue 本文の差分（消えたキー・型が変わったキー・新しいキー、HTTP ステータス）を読む
- 該当する zod スキーマと正規化関数を特定する
- エージェントは note.com にアクセスしない。新しいレスポンスが必要なら、取得したいエンドポイントと理由を Issue にコメントし、人に fixture の取得（record スクリプトの実行）を依頼して止まる

## 2. 影響を分類する

| 状況 | 対応 |
| --- | --- |
| 使っていないキーの変化 | スキーマを緩める（`passthrough` 等）だけ。公開型は不変 |
| 使っているキーの改名・型変更 | 正規化で吸収する。新旧どちらの形も受け付けるテストを書く |
| 取得できなくなった（404・405 等） | RSS への自動切り替えが働くことをテストで確認し、README の注意書きを更新する |
| 公開型を変えないと対応できない | 実装せず、案を Issue に書いて人の判断を待つ |

## 3. 修正する

- 新しい fixture（人が取得したもの）を使い、失敗するテストを先に書く
- 旧形式の fixture のテストは消さない（両方の形を受け付ける）
- `pnpm check` を通す

## 4. PR

- changeset は patch（note 側への追従は即パッチリリース）
- PR に「note 側の何が変わったか」「利用者への影響」「公開型の変更有無」を書き、`Closes #N` を入れる
- 計画では障害の Issue から3日以内に修正版を出す。人のレビューを依頼する
